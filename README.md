Online platforms receive far more comments than human moderators can read, and the language of toxic comments keeps changing.
This project builds a system that scores every new comment for toxicity and decides: publish, send to human review, or hide.
It uses the Jigsaw Unintended Bias (Civil Comments) dataset, split by time so that new months can be replayed as new batches.
The system watches its own inputs and predictions for drift, and a human approves any retrained model before it goes live.
The goal is to catch most toxic comments quickly while keeping the human review queue small and the whole system reproducible from this repository.

Full design: docs/design.md

## Lab 3: LLM baseline and retrieval

### LLM component

- **Job:** same task as Lab 2: the LLM scores the toxicity of a comment (0-1). Metric = Lab 2 metric (PR-AUC, recall at precision ≥ 0.50),
  computed on a random sample of <<600>> validation comments (2017-04 → 2017-05), together with the rule and the champion on the same sample.
  Second use: retrieval over moderation guidelines adds top-k guideline chunks to the prompt.
- **Corpus:** 16 short moderation-guideline documents in `corpus/` (LLM-generated, then read and edited by hand; synthetic, public in this repo;
  the thresholds in them are assumptions of this project). Chunks: 32 (chunk size 120 words, overlap 20).
  the thresholds in them are assumptions of this project). Chunks: <<N>>.
- **Config:** everything (chunk size, overlap, embedding model, top-k, LLM address and model, prompt paths) is in `configs/rag.yaml`.
  Prompts: `prompts/*.txt`, their sha256 prefixes are logged as tags `prompt_hash_*` on every run.
- **Inference:** <<vLLM `Qwen/Qwen2.5-0.5B-Instruct` on CPU in Docker, locally built image / API model X>>.

### Rebuild the index (one command)

```bash
make rag-index        # indexed <<32>> documents, <<N>> chunks (pgvector, schema rag)
```

### Evaluation set

`eval/questions.jsonl`: 21 questions, each with relevant document id and reference answer.
**read and filtered by me**. Questions are paraphrases: `make rag-check` fails if a question contains the document title, its slug or a 5-word phrase of it.
Questions are generated by a different model than the one that answers, to reduce same-model bias.
Answer metric: LLM-as-judge (`prompts/judge_v1.txt`, hash logged), scale 0/1/2 normalised to [0,1]; I checked 10 judged answers by hand, agreed on 10.

### Results (LLM classifier vs Lab 2, same 20-comment sample)

The LLM is run on a **20-comment random sample** of the validation period (2017-04 → 2017-05, seed 42), limited by free-tier API quotas.
Rule and champion are scored on the same 20 comments. Metrics are the Lab 2 metrics, logged under the same names (`val_pr_auc`,
`val_recall_at_p50`) in experiment `llm-rag`.

| (same 20 comments)                 | PR-AUC | recall @ precision ≥ 0.50 |
| ---------------------------------- | ------ | ------------------------- |
| rule (bad words)                   | 0.30   | 0.50                      |
| TF-IDF + LogReg (champion)         | 0.83   | 1.00                      |
| LLM zero-shot (qwen3.8-27b)        | 0.33   | 0.00                      |
| LLM + retrieval (k=3, qwen3.8-27b) | 0.15   | 0.00                      |

**Caveat.** With ~8% toxic comments, a 20-comment sample contains only <<N>> positives, so one comment moves PR-AUC and recall by tens of
percentage points. These numbers show that the LLM run is tracked, parsed (0/20 parse failures) and comparable with the Lab 2 baselines
in the same UI; they do **not** support a conclusion about which model is better. On this sample the champion scored highest, which is
consistent with it being trained on this task, but I make no claim beyond that. A larger sample (`eval.classify_n` in `configs/rag.yaml`)
reruns with one command once quota allows.

### Retrieval experiment: one parameter, three values (`make rag-sweep-chunk`)

Fixed: top-k = 3, overlap 20 words, same 21 questions, same prompts. Only the chunk size changes (the index is rebuilt for each value).

| chunk size (words) | chunks in index | hit rate@3 | MRR   | answer score | run id                           |
| ------------------ | --------------- | ---------- | ----- | ------------ | -------------------------------- |
| 60                 | 63              | 0.905      | 0.861 | 0.643        | 471eed081a8d402a89b8e68299247f9a |
| 120                | 32              | 1.000      | 0.937 | 0.929        | 464cda41e865424caaa103abbedc6bfc |
| 240                | 16              | 0.952      | 0.837 | 0.905        | e90090c9ea3f4f268c505dc184a1216a |

Reading: 120 words is best on every metric. At 60 words a document is split into ~4 pieces, so a retrieved chunk often lacks the sentence
that holds the answer: hit rate and especially the answer score drop (0.929 → 0.643). At 240 words every document is one chunk (16 chunks
for 16 documents), so retrieval is document-level; the answer score stays high, but MRR falls (0.937 → 0.837), because longer chunks have
a more diluted embedding and the right document ranks lower. Caveat: with 21 questions one question moves hit rate by 0.048, so the
120 vs 240 hit-rate gap is a single question; the answer-score gap at 60 words is large enough to be real.

### Cost and latency (from the runs, `llm-rag` experiment)

| run                  | calls      | tokens in / out | cost        | p50 / p95 latency | first call       | API time (sum) |
| -------------------- | ---------- | --------------- | ----------- | ----------------- | ---------------- | -------------- | -------- |
| llm-zeroshot         | 20         | 3 558 / 245     | 0 USD       | 0.15 s / 0.26 s   | 0.68 s           | 3.51 s         |
| llm-rag (k=3)        | 20         | 10 155 / 258    | 0 USD       | 0.21 s / 4.21 s   | 0.67 s           | 24.04 s        |
| chunk-120 (rag-eval) | answer LLM | 21              | 9 376 / 954 | 0 USD             | 0.35 s / 31.02 s | 0.98 s         | 130.08 s |
| chunk-120 (rag-eval) | judge      | 21              | 3 995 / 150 | 0 USD             | 0.29 s / 1.34 s  | 0.48 s         | 8.58 s   |

Latency is measured on the HTTP call only (successful attempt), the client additionally paces requests (≥4.1 s apart) to stay inside the
free-tier rate limit, so wall-clock time is longer than the sum of call times (24.04 s of API time for 20 calls).
Tokens are as reported by the provider. Cost is 0 because the free tier is used (price fields in `configs/rag.yaml` are 0).

The retrieval variant scored lower than zero-shot (PR-AUC 0.15 vs 0.33) on these 20 comments. With so few positives this difference is
not meaningful; a plausible cause worth testing on a larger sample is that guideline chunks retrieved for an arbitrary comment are only
loosely related to it and add noise to the prompt.

Chosen setting (chunk 120, k=3): hit rate@1 = 0.90, @3 = 1.00, @5 = 1.00, MRR = 0.94, answer score = 0.93,
citation_not_retrieved_rate = 0.00 (no answer cited a document the retriever did not return), judge parse failures 0/21.

```bash

SELECT c.batch_month, c.n AS comments, f.n AS features
```

### 5. Train: rule vs model, tracked in MLflow

The working tree must be clean (training refuses a dirty tree, otherwise the `git_commit` tag would be false):

```bash
git add -A && git status        # no .env, data/broken, data/interim, reports
git commit -m "Lab 2: pipeline, training, docs"

```

- MLflow http://localhost:5001 → experiment `toxicity-baseline`: runs `rule-badwords`, `tfidf-lr`, `tfidf-lr-RANDOM-SPLIT-LEAKY`.

- Artifacts tab of `tfidf-lr` is stored in MinIO bucket `mlflow`.

### 6. Register the model with lineage

```bash
make train-register             # registers toxicity-tfidf-lr, tags both identifiers, alias "champion"
git push origin main            # the commit from the tag must exist for reproduce
```

- MLflow http://localhost:5001 → Models → `toxicity-tfidf-lr` → version 1: tags `data_version`, `git_commit`, alias `champion`
  (screenshot of runs and model → `docs/img/mlflow_runs.png`).

### 7. Reproduce the registered model with one command

```bash
make reproduce MODEL_VERSION=1
```

It reads the tags from the registry, checks out that commit in a `git worktree`, runs `dvc pull` (md5 verified), rebuilds the
warehouse months with the same code, retrains and compares `val_pr_auc` with the original (tolerance ±0.005).

- The last line must be `... -> PASS` (paste it into the README).
- MLflow http://localhost:5001 → a new `tfidf-lr` run with tag `reproduces_model_version=1`.
